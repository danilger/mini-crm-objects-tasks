# Решения и допущения

## Что решили сами

1. **Роли в таблице `profiles`**, а не в `user_metadata`: проще писать RLS и показывать на созвоне.
2. **Смена статуса только через RPC `transition_task`**. Прямой `UPDATE` статуса блокируется триггером. Так проще обязательный комментарий при возврате на доработку и единая точка проверки переходов.
3. **История**: запись при создании задачи (триггер) и при каждом `transition_task`. Клиентам разрешён только `SELECT`.
4. **Статусы как Postgres enum** (`new`, `in_progress`, `in_review`, `rework`, `accepted`) — на UI русские подписи.
5. **UI**: Tailwind без shadcn, чтобы уложиться в 2–3 часа; дизайн по ТЗ не оценивается.
6. **Auto-expose new tables выключен**, **automatic RLS включён** — доступ к таблицам через явные `GRANT` + политики.
7. Имена ролей в коде: `manager` / `worker` (постановщик / исполнитель).

## Что нужно сделать вручную в Supabase Dashboard

1. Выполнить `supabase/migrations/20260326000000_init.sql` в SQL Editor.
2. Подставить UUID трёх пользователей в `supabase/seed.sql` и выполнить.
3. Отключить публичную регистрацию (Authentication → Providers → Email → Disable sign ups).
4. Прописать `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` во фронте (локально и на хостинге).

## Что может быть не сделано / упрощено

- Нет редактирования объекта/задачи «в один клик» сверх базовых форм.
- Нет Realtime-подписок — обновление после действий через перезагрузку данных.
- Автотесты UI не писались; есть скрипт `scripts/verify-rls.mjs` для проверки прав через API.
- Self-hosted Supabase и свой nginx не использовались — облачный Free tier + статический хостинг фронта.
